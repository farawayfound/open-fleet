Active jobs

Everything the fleet is working on right now — inference in flight, batch fan-outs, benchmarks and model downloads.
Aborting an inference request closes the connection to the box serving it, which is what makes llama-server free the decode slot — the client sees a truncated reply and the tokens already produced are still metered. A batch keeps the answers it has. A download keeps its partial file and resumes where it stopped.

Fleet storage

Model volumes across the fleet. The lighter segment is space already committed to in-flight downloads — “free after” is what you will actually be left with when they land.

Batch jobs — fan-outs dispatched by this hub across every box that can serve them

One shared queue per job; every host serving the job's model gets as many workers as that model has decode slots there, so a fast box simply takes more of the queue. A host going down mid-job costs retries, not the job. Finished jobs age out with the telemetry window; archived ones keep their results until retention deletes them.

}

GET  /v1/batches/<id>/results    → NDJSON: {"i", "ok", "status", "model", "host", "ms", "body"}
POST /v1/batches/<id>/cancel
Give models a list when more than one model is acceptable for the job — that is what spreads it across machines that serve different models. Each host is assigned exactly one of them, first listed wins, because a llama.cpp box reloads on every model switch.

Teams

A team is an OpenAI-compatible API key that fronts a crew instead of a single model. The primary model leads the conversation; the gateway hands it a spawn_subagents tool, executes any spawned tasks in parallel across whichever fleet boxes serve the worker models, feeds the results back, and returns one ordinary chat completion — the client never knows the fleet exists. Point any OpenAI client at the base URL with the team's key and it gets Claude-Code-style parallel sub-agents for free.

GPU memory allocation

      

      

      

        

          

        
        
        
        
      

      
On an APU the BIOS UMA carve-out (dedicated VRAM) is
        firmware-only, but GTT — the extra window the GPU maps out of
        system RAM — is a kernel parameter, staged here and applied on
        reboot. Raising GTT lets llama.cpp address more than the BIOS
        carve; every GiB of GTT is a GiB the OS no longer has.

Existing keys

    

      
      
      
    

    

    

    
Delete archives a key: it stops authenticating at once — every client
      using it gets a 401 — but the row survives, so revoking the wrong one is recoverable. A hashed
      key cannot be re-minted, which is exactly why this is not a real delete. Restoring brings it
      back disabled; enabling is a second, deliberate click. Archived keys are permanently
      deleted after the retention period (Telemetry ▸ History & retention).

Agent profiles

    
An agent profile shapes every request made with its key,
      enforced at the gateway — the client cannot see or bypass it. The system
      prompt and rules are injected as the first system message; the model
      allow-list rejects anything else with 403; parameter overrides fill in
      sampler defaults the client left unset (max_tokens acts as a
      hard cap).

    

      
      
      
    

    

    

    
Removing a profile archives it: injection stops immediately, and a system
      prompt you spent an afternoon on is still there if that was a mistake. Archiving a key
      archives its profile with it.

History & retention

  

    

      
Windows for this host

      
Every list on this dashboard has three ages.
        Live inside its window — shown by default, one page at a time. Archived once
        it ages out or you file it away: gone from the default view, still in the database, still
        restorable. Deleted for good only after it has been archived for the full retention
        period. Nothing here is destroyed in one step.

      

        

          

        

          

        

          

        

          

      

      

      

        
        
        
      

      
Retention is counted in calendar months from the day a row was
        archived — 12 means this date last year, not 360 days. Both jobs run automatically at
        startup and once every 24 hours; “Purge expired” only takes what the table beside it counts
        as due. Settings are per host.
